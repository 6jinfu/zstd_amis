# 景旺客户需求分析与人才中心设计建议

> 2026-09-29 最新范围修正：用户明确不接受“已保存视图”，该候选建议不纳入本期功能；以当前 PRD V1.30 为准。

分析日期：2026-09-29  
文档性质：需求分析与候选设计方案，供范围决策和原型设计使用；尚未作为当前版本需求基线。  
依据：2026-09-28 FlowUs 日报、项目交接文档、当前 PRD 和当前页面代码。未读取完整会议转写，也未验证客户线上生产系统。

## 1. 核心判断

客户连续询问岗位匹配、胜任判断、晋升认证、自主发展、标签找人、档案和报表，说明其关注点可能已经从“开展培训与盘点”延伸到“如何使用盘点结果作出人才决策”。这是根据问题组合形成的需求假设，日报中的“不支持”不能直接等同于客户已确认的采购必选项。

建议把人才中心定位为：**以人员为主线，汇集标准、评鉴、盘点与发展证据，支持人才查找、候选比较、持续培养和后续任用衔接。**

优先解决三个断点：
t
1. 结果分散：人员的能力、盘点和学习记录缺少连续视图。
2. 查找困难：知道想找什么样的人，却不能按业务条件筛选。
3. 后续管理中断：选出一批人后，缺少跨项目人才池、培养跟进和复评记录。

岗位自动匹配、正式资格认证、晋升调岗审批建立在上述基础上，应分别确定责任系统和实施条件。

## 2. 当前项目的真实起点

| 项目现状 | 对设计的影响 |
| --- | --- |
| 人才中心只有人才列表；详情只有综合能力、最新盘点结果 | 可以沿现有人才列表与详情扩展，不需要重新建立人员主数据 |
| 人才列表只有姓名、人才分类筛选；对比只含能力和最新盘点 | 查找、比较和结果使用是最直接的改进位置 |
| 宫格盘点已有项目人才池，人才图谱没有人才池入口 | 独立人才池须作为新范围建设，保留既有项目记录及来源；不能直接将项目池改成全局池 |
| 当前人才详情按已选标准展示要求，与实际能力对比 | 是岗位差距分析的基础，但不等于已有跨岗位匹配或正式胜任判断 |
| 岗位地图已有多通道矩阵；学习方案仍以岗位资源清单为主 | 路径配置继续归发展中心，方案发布、分配和执行跟踪仍需补齐 |
| 学员端已纳入产品规划，但参考包尚未按当前模型重构 | “我的画像”“我的发展计划”不能视为已落地能力 |
| 跨项目人才池、组织人才看板、完善档案已写入 9 月 28 日深化方向 | 本方案与既有方向一致，但具体页面、字段和业务规则仍属新增设计建议 |
| 当前项目是静态高保真原型，部分数据使用浏览器本地存储或会话状态 | 可点击演示与真实生产能力须分别验收；身份、权限、接口、持久化仍需实施 |

## 3. 八项不支持功能的需求拆解

| 日报中的功能问题 | 客户可能要完成的工作 | 需要补足的业务规则 | 建议落点与顺序 |
| --- | --- | --- | --- |
| 选、用、留全链路 | 将盘点产生的人选用于后备培养、岗位补缺和任用讨论 | 谁提出人选、谁决定、结果交给哪个系统、谁跟踪后续 | 人才中心先提供候选名单、人才池、建议与回执；晋升、调岗、任命流程按 HR 系统边界另定 |
| 自动匹配适配岗位 | 以岗找人，或帮助一个人发现可发展的目标岗位 | 候选范围、岗位标准、必备条件、证据有效性、员工意愿 | 先做人工选择目标岗位后的差距比较；证据完整后再做基于规则的候选推荐 |
| 输出胜任／不胜任 | 管理者需要可解释的岗位准备情况，用于培养或任用讨论 | 对什么岗位、什么标准版本、由什么证据、谁确认 | 人才档案和人才对比先显示逐项要求与差距；正式资格结论另建确认流程 |
| 员工自主申请晋升／认证 | 员工表达发展意愿、获知门槛、申请进入评估 | 申请是否常开、周期、资格、材料、受理人、审批人 | 学员端可先提出发展意向，由上级确认；认证申请和晋升申请分别设计 |
| 动态、自主选择的发展路径 | 横向转岗、跨通道发展、看到不同岗位的进入条件 | 允许哪些转移、前置条件、目标确认、标准与方案关联 | 发展中心维护路径关系和进入条件；人才中心使用目标岗位和差距结果 |
| 按人才标签找人 | 快速找到具备指定能力、经验或培养资格的人 | 标签来自哪里、能否量化、有效期、多条件组合、谁能看 | 首期增强人才列表筛选和保存视图；能力指标与人工标签分别管理 |
| 档案整合盘点评鉴 | 开会讨论人才时，能在一个地方看到事实、变化和依据 | 人员唯一标识、记录来源、周期、冲突、员工可见范围 | 首期重构人才档案；管理端与学员端基于同源数据呈现不同范围 |
| 全维度人才报表 | 看清人才储备、关键岗位缺口和培养效果 | 指标定义、分母、统计时间、组织范围、可比性 | 数据汇聚后建设人才看板，先提供少量可钻取的标准主题 |

特别说明：“留”只在全链路概括中出现。现有材料不足以支持离职风险预测、薪酬保留方案或员工敬业度系统立项。应先确认客户实际存在的保留管理工作。

## 4. 功能归属与职责

| 位置 | 应负责的工作 |
| --- | --- |
| 人才标准 | 指标、标准内容、应用范围及后续标准版本；不在人才档案另建一套能力词典 |
| 评鉴中心 | 产生测评、考试、360 和盘点证据；未来如开展岗位认证，负责评估证据与专业判定环节 |
| 发展中心 | 岗位地图、通道关系、发展方案、发布分配和任务完成规则 |
| 人才中心 | 以人员汇集证据、筛选比较、管理跨项目人才池、跟踪发展与复评、呈现组织人才情况 |
| 学员端 | 个人画像、发展意向、计划执行、成果提交；自主申请按企业政策开放 |
| 既有 HR 系统 | 组织岗位与任职主数据，以及经边界确认后的晋升、调岗、任命审批与生效记录 |

人才中心可提供“安排发展”“查看评鉴”“提交任用建议”的业务入口，但必须链接到负责该流程的对象和系统。一个人员详情页不应独立创建第二套测评、计划或人事审批流程。

## 5. 推荐的信息架构

```text
人才中心
├─ 人才库（沿现有人才列表升级，默认入口）
│  ├─ 搜索、条件筛选、保存视图
│  ├─ 人才对比、按目标岗位比较
│  └─ 人才档案
│     ├─ 概览
│     ├─ 标准与差距
│     ├─ 评鉴与盘点
│     └─ 发展记录
├─ 人才池（新增，跨项目持续管理）
│  ├─ 人才池列表
│  └─ 人才池详情：成员、目标、培养与复评
└─ 人才看板（数据条件具备后新增）
   ├─ 人才结构与数据覆盖
   ├─ 关键岗位储备
   └─ 人才培养进展
```

首轮原型重点是人才库、档案、比较和人才池。人才看板在统计口径明确后进入下一批；岗位匹配先作为人才库和档案中的情境操作，不急于新增独立菜单。

沿用当前左侧一级中心、顶部业务入口、白底、主蓝和固定分页规范。通过筛选、字段与操作提升使用效率，不新增装饰性首页和缺少来源的统计卡片。

## 6. 人才库如何优化

### 6.1 从浏览名单转为按业务条件找人

保留姓名搜索，补充部门、岗位、关键岗位、人才分类；人才分类筛选同时选择来源盘点项目或明确“最新有效结果”的规则。部门筛选明确是否包含下级部门。

高级条件分批增加：

- 能力条件：指标、比较关系、要求等级、结果有效期。例如“项目管理达到企业定义的 3 级，且有有效评鉴证据”。
- 评鉴与盘点条件：项目、周期、落位或分层；不把不同项目的同名分类自动合并。
- 人才池与发展条件：所属人才池、目标岗位、计划状态；只在对应功能实际建立后开放。
- 人工业务标签：如“海外项目经历”，需有维护人、依据和有效范围；不把自由标签当成能力评定。

首期采用同组条件全部满足，多选值任一满足，避免立即建设复杂表达式编辑器。用户可以保存筛选视图，但保存视图每次查询会变化；已确认的人才池成员按成员记录持续管理，两者不能共用对象。

### 6.2 列表和操作

默认列建议为：姓名、部门、岗位、职级（有明确数据源后）、人才分类及来源时间、最近评鉴时间、所属人才池、操作。目标岗位和差距只在开启目标岗位比较时显示。

性别、学历、司龄保留在档案或可选列，列表默认优先展示支持本轮管理决策的信息。缺少结果明确显示“暂无有效结果”，不显示零分。

勾选后提供：对比人才、加入人才池、安排发展、按权限导出。跨页选择显示实际选择范围；批量操作预览人员名单，避免把“当前页”误当作“全部结果”。发展安排入口依赖方案发布与分配能力，未完成时不放演示性成功按钮。

## 7. 人才档案如何优化

| 模块 | 主要内容 | 支持的判断或动作 |
| --- | --- | --- |
| 概览 | 身份、组织岗位、当前标准、已确认发展目标、所属人才池、最近有效结果摘要、待跟进事项 | 快速理解这个人的当前情况，并进入具体依据 |
| 标准与差距 | 当前标准或所选目标岗位标准、五类要求、对应证据、达标／差距／缺证状态 | 决定需要补评什么、培养什么；切换岗位只改变比较目标，不改变人员证据 |
| 评鉴与盘点 | 360、有效考试与测评记录、历次盘点及校准记录、来源项目与日期 | 查看结论怎么形成；进入原项目，查看变化是否可比 |
| 发展记录 | 已分配计划、任务进度、实践成果、反馈、前后测、已确认发展结果 | 区分“完成学习任务”与“已有证据证明要求达到” |

采用现有详情导航方式扩展，不把所有数据塞在一个长页。概览显示摘要，明细进入相应模块，避免在多个页签重复同一张雷达图。

“统一档案”首先统一人员身份和记录关联，允许点击回到来源系统，不要求首期复制培训平台的全部学习行为。

### 7.1 岗位差距的核心呈现

每条要求至少显示：要求内容、要求等级或条件、当前证据、来源与日期、证据是否有效、状态。职责任务和经历经验不能只靠能力雷达图代替；没有结构化证据时允许人工补充、待核验，不能推断已满足。

建议显示三个独立维度：

1. **证据覆盖**：适用要求中，有可用于判断的有效证据有多少。
2. **已评估要求的满足情况**：仅在已具备证据的要求中统计；与覆盖情况一起展示。
3. **必备条件情况**：全部满足、存在未满足、存在待核验；不让高分抵消必备条件未满足。

例如，某岗位共 10 项适用要求，只掌握 4 项有效证据且都满足，应显示“证据覆盖 4/10；已评估要求满足 4/4；6 项待补充”，不能显示“岗位匹配度 100%”。

首期不输出未经验证的统一匹配百分比。展示结论可用“已评估要求符合”“存在待发展项”“证据待补充”，并始终带上具体目标岗位、标准版本与评估时间。

如以后需要正式岗位资格结论，应有评估范围、证据清单、认定人、认定时间、有效期和复核机制；资格认定通过也不直接改变员工任职。

## 8. 人才对比与岗位匹配

沿用现有 2—5 人对比，但补充标准、证据和差距明细。进入比较前可选择一个共同目标岗位及标准版本。

比较表按同一要求展开：要求、每人的有效证据、差距、待核验项、更新日期。某人缺少结果显示缺证；不同岗位标准下的综合能力雷达不用于得出谁更适合目标岗位的结论。

“以岗找人”建议按以下顺序发展：

```text
明确目标岗位与采用标准
→ 确定候选组织范围和必要条件
→ 查询符合条件与待补证据的人选
→ 人工比较证据、确认候选
→ 加入人才池或安排发展
```

自动推荐建立在稳定规则之上：显示命中的条件、差距和缺失依据，不把 AI 推断当成人员事实。员工意愿和可流动性若未采集，显示“待确认”。AI 可用于理解查询、解释证据和起草培养建议；人选录用、岗位资格和任职变更由授权人员确认。

## 9. 跨项目人才池如何设计

人才池是有持续管理目标的一组人，应绑定用途、负责人及复评安排。例如“区域负责人后备池”要回答：为哪些岗位储备、需要多少人、谁负责培养、什么时候复评。

**人才池字段：**名称、用途、负责组织、负责人、目标岗位（可选）、采用标准版本（涉及岗位准备情况时必需）、期望规模（可选）、复评安排、状态。

**成员字段：**人员、入池来源及日期、入池理由、确认人、目标岗位、当前发展计划、最近复评、下次跟进、成员状态及退出原因。

成员状态首期只需区分“在池／已退出”，有独立入池审核需求时再增加待确认状态。培养进度、证据准备情况、任用结果分别记录，不混进一个状态字段。

成员来源可以是人才库人工选择、已结束盘点的人员结果、管理者提名。一个人可进入多个池，同一池内去重，多次来源记录保留。首期规则筛选只提供建议名单，由负责人确认入池；后续数据变化不自动删除成员。

与现有项目池的衔接采用“加入持续管理的人才池”，记录来源项目及当时依据。项目池继续保留本次盘点记录，独立池承接之后的培养和复评；退出独立池不改写历史盘点。

人才池详情应让负责人直接看见待安排发展、计划逾期、待复评人员，并执行对应动作。已完成计划的成员可发起复评；计划完成不能自动标记为岗位胜任或已任用。

## 10. 自主申请、路径与任用如何衔接

需要区分四件事：

| 业务事项 | 结果 | 建议承接方式 |
| --- | --- | --- |
| 发展意向 | 员工表达想发展的方向，上级确认目标 | 学员端提交，上级或 HR 确认后进入人才档案和计划 |
| 认证申请 | 请求启动针对标准的评估或资格认定 | 条件、周期与认定规则明确后建设，复用评鉴证据 |
| 晋升／调岗申请 | 请求改变任职、职级或岗位 | 以客户现有 HR 审批体系为依据确定入口与流转 |
| 任职生效 | 正式组织岗位记录发生变化 | 由任职主数据所属系统确认并同步 |

因此，“员工不能自主申请”不意味着员工只能被动接受安排。可以先支持表达发展意向、查看要求、接收反馈；是否允许发起正式认证和晋升分别由企业政策决定。

动态发展路径继续在发展中心设计。后续需要在岗位节点之间记录“可发展到哪个岗位、关系类型、进入条件、关联方案”，支持向上和横向关系。多通道矩阵展示不能替代这些关系规则。

若客户需要闭环衔接任用，人才中心可生成带证据的人选建议，提交后记录外部流程编号、当前状态、结果和生效时间。没有真实接口时，原型明确展示模拟或人工回填流程，不能声称审批已打通。

## 11. 人才看板先做哪些内容

先建设三个标准主题，每个指标都能钻取到与统计口径一致的人员名单。

| 主题 | 首批指标或分析 | 数据要求 |
| --- | --- | --- |
| 人才结构与数据覆盖 | 组织、岗位人员分布；有效评鉴覆盖率；不同盘点项目的分类分布 | 人员范围明确，结果有效性和盘点来源明确 |
| 关键岗位储备 | 有已确认在池后备人选的关键岗位数、无后备岗位清单、后备人员证据准备情况 | 目标岗位与池成员关联、在池状态、共同标准与有效证据 |
| 人才培养进展 | 已分配计划人数、到期完成情况、逾期人员、待验证成果、可比较的复评变化 | 真实发布分配记录、任务状态、成果验证和前后结果 |

关键指标建议口径：

- 有效评鉴覆盖率＝统计范围内至少有一条有效评鉴结果的去重人数／范围内应评人数。另列岗位要求的证据覆盖，不能用“测过一次”替代“要求已评全”。
- 关键岗位后备覆盖率＝至少有一名已确认在池后备人员的关键岗位数／纳入储备管理的关键岗位数。有人选不代表人选已经准备就绪。
- 到期计划完成率＝截至统计时点已到期且完成的计划数／截至该时点已到期的有效计划数；明确终止计划的排除规则。
- 能力变化仅对同一指标、可比较标准和评价方式的配对结果计算；同时报告可比较人数，不跨量表直接相减。

所有看板明确组织范围、统计时点或周期、分母、缺失数据。当前组织分布和历史项目所属组织分开使用，避免人员调岗后改写过去的组织表现。报表导出与页面钻取采用相同过滤条件和可见权限。

## 12. 设计前必须统一的数据规则

### 12.1 最高等级与当前水平

现 PRD 对人才能力汇总采用有效结果中的最高等级。最高表现和当前岗位准备情况是不同用途。设计正式岗位比较前，建议明确：哪些结果在有效期内、采用哪种来源、冲突怎样处理、历史最高是否只作参考。具体取值策略需要业务确认，不能在设计中悄悄改成“取最近一次”。

### 12.2 缺失数据

当前宫格盘点规则存在“缺少能力结果按 0 分计入”，而人才档案又要求无有效结果不伪造实际值。岗位准备情况必须区分“已评估未达到”和“尚无证据”。建议单独定义新场景的缺证规则，并评估现有盘点规则是否需要版本化修订；不得回写覆盖已结束项目。

### 12.3 盘点分类的适用范围

人才图谱 A/B/C/D 是项目样本内相对分层，不能直接转换为通用岗位资格或跨项目排名。宫格文案也可以自定义，两个项目的“核心人才”未必依据相同。

人才档案保留“项目、周期、方法、规则版本、结果”；默认展示哪条结果须有确定规则，列表分类筛选与看板保持一致。历次变化仅在口径可比时解释为提升或下降。

### 12.4 指标、标签和标准

- 能力、动力、潜力是评鉴指标，有字典和证据来源。
- “后备干部”“海外项目经历”等是业务标签，需有维护依据。
- 人才标准定义岗位或人群要求；一个岗位可能关联多套标准，比较时必须明确采用哪一套。
- 标签可以辅助查询，但不能绕过评鉴过程生成能力等级或潜力结论。

### 12.5 人员、权限与历史

以员工唯一标识关联 HR、评鉴、培训和发展记录，姓名不作关联键。组织岗位数据和任职结果明确权威来源；人才中心管理人才池、发展目标和跟进记录。

HR 按授权组织范围查看；管理者按团队或项目授权查看；导师只看承担的计划与成果；员工看自己的标准差距、计划和反馈。管理端潜力结论、盘点分类和候选排序按现有原则不默认向员工开放。搜索、导出和统计钻取均遵守相同范围。

变更标准、调岗、退出人才池、取消计划均保留历史。历史盘点、比较结果和正式认定记录使用当时的标准与证据，不随当前档案更新而重算。

## 13. 一条应优先验证的完整场景

以“选出并培养区域负责人后备人选”为设计验证场景，以下为建议演示流程，不是已经确认的客户实际制度。

1. HR 选择目标岗位“区域负责人”和适用标准，确定候选组织范围。
2. 从人才库按能力证据和已结束盘点条件筛选，看到每人满足项、差距和缺证项。
3. 选择 2—5 人按共同标准比较，业务负责人确认候选。
4. 加入“区域负责人后备池”，记录依据、负责人和复评日期。
5. 根据差距选择已发布的发展方案，为人选分配计划；员工确认接收。
6. 员工完成学习与实践，上级审核成果，组织相应复评。
7. 人才档案和人才池更新准备情况，保留原始结果和本次变化。
8. 需要任用时输出带证据的建议，交由约定的 HR 流程处理，再记录正式结果。

这条链路能同时验证查找、档案、比较、人才池、培养、复评和系统衔接。首轮原型可先完成第 1—4 步及第 5 步的明确跳转，后续在发展方案发布链路具备后继续贯通。

## 14. 分期与验收建议

暂不做数值化 RICE 排名：目前只有一次会议的功能询问清单，缺少使用频次、覆盖人数、业务损失和工程成本。以下顺序依据依赖关系与现有项目基础提出。

| 阶段 | 建议范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| 第一阶段：找人、看依据、持续管理 | 人才库筛选；档案四模块中的可用数据；共同目标标准比较；跨项目人才池和来源记录 | 人员身份、标准、证据与分类口径可追溯；权限范围明确；从查找到入池可完整操作 |
| 第二阶段：培养与复评闭环 | 发展方案发布分配；计划与成果回流；池内跟进与复评；人才看板首批主题；发展意向 | 培训平台状态与评鉴结果可回传；复评与前后变化具备可比规则 |
| 第三阶段：匹配与任用衔接 | 规则化岗位推荐；条件成熟时的资格认定／认证申请；HR 任用流程对接；更灵活的发展路径 | 客户制度、责任人、接口、标准版本及认定规则明确，并具备足够有效数据 |

阶段内的依赖功能按实际完成度开放，不给尚未建设的流程配置无效菜单。

首轮原型建议覆盖六个主要界面：人才库、筛选抽屉、人才档案、同标准人才对比、人才池列表、人才池详情。使用一组贯穿全部页面的人员、标准、证据和计划数据，避免每页单独编故事。

验收至少验证：

1. 筛选结果符合所选指标、等级、有效期及数据范围，缺证人员按设定规则单独识别。
2. 保存视图重新计算，人才池成员保持确认记录；数据变化不会悄悄改变已入池名单。
3. 人才档案的每个结果能追溯来源；切换目标标准不改变人员实际证据。
4. 对比使用相同标准版本，缺证不会计为达标或用其他不相关结果补齐。
5. 从项目人才池加入独立人才池保留来源，重复选择不产生重复成员，退出保留历史。
6. 培养任务完成与要求验证分别显示，验证结果有依据；无法回传时显示真实待同步或待确认状态。
7. 看板人数与钻取名单、导出一致，不合并不可比项目的排名或分类。
8. 不同角色看到的内容与操作范围一致，敏感管理结论不从导出或搜索结果泄漏到学员端。

可用于后续观察的成效指标：产出合格候选名单所需时间、候选证据完整率、后备池成员按期复评率、到期发展计划完成与验证情况。基线和目标数值需在真实工作流程中采集后确定。

## 15. 客户下一轮沟通应优先确认的事项

这些问题影响设计方向，应让客户结合最近一次真实案例回答：

1. 最近一次要选拔、调岗或培养谁，涉及哪些岗位、多少人，在哪一步最费时？本次询问中哪些会影响采购或落地？
2. 岗位标准是否已有分级要求和正式资格门槛？“胜任”由谁认定，是否允许人工覆盖，证据多久失效？
3. 更常用“为岗位找人”还是“为员工找方向”？是否跨部门选人，员工意愿由谁确认？
4. 自主申请指发展意向、参加认证还是正式晋升？各自的开放周期、受理人和审批流程是什么？
5. 人才池是否长期存在，谁负责，什么条件入池、退出、复评？盘点结果之后目前如何跟进？
6. 现有 HR、培训、测评系统分别提供哪些人员标识、结果与流程接口？客户说的“统一档案”主要供 HR、主管还是员工使用？
7. 最常用的三张人才报表分别支持什么决策，分母和统计周期是什么？

## 16. 需要在后续正式设计中同步的现有文档项

本次仅提出候选方案。确认纳入范围并开始改原型时，应同轮更新当前 PRD 和 PROJECT_HANDOFF.md，特别是：

- 人才中心仅保留列表的当前边界，以及独立人才池和组织看板的延期状态。
- 人才详情只保留综合能力、盘点结果两模块的限制。
- 列表筛选与 AC-05“按标签筛选”的现存不一致。
- 岗位准备情况采用的能力证据规则，与当前最高等级汇总、盘点缺失记零规则的关系。
- 学员端发展意向、目标确认与申请权限。
- 跨项目人才池与项目人才池的关系、成员状态和数据实体。
- 正式资格认定、任用建议与 HR 生效记录的职责边界。
